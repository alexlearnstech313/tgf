# SECURITY-OUTPUT-ENCODING — Rules

Seven rules extending SECURITY-CORE Rule 5.6 (*Output Encoding Matches Context*) with operational depth. SECURITY-CORE remains canonical for the universal principle (encode at the consuming context; never assemble data into interpreted strings). The rules below add the *which contexts*, *which encoding*, and *what breaks* layer.

Per Phase 6 Checkpoint 1 Decision A: chapter-level citations live in `SKILL.md §2 Authoritative Sources`; sub-rule citations (V1.1.1, V1.2.4, etc.) appear here where mapping is crisp and verified live.

Per Phase 6 Checkpoint 1 Decision B: hard-refusal patterns covered by SECURITY-CORE are referenced by ID, not restated.

## Rule 5.1: Encode at the Interpreter Boundary, Once, in Canonical Form

**Statement:** Encoding happens at the boundary where data is consumed by an interpreter — the SQL driver's parameter binding, the HTML rendering call, the process spawn, the LDAP query, the XML serializer, the logger emit. Data is decoded to a single canonical form on input (one URL-decode pass, one HTML-entity-decode pass) and *not* pre-encoded for storage. Encoding for the consuming context happens at the output boundary itself. Double-encoding (encoding at input *and* at output) breaks rendering; pre-encoded storage (storing HTML-escaped text in the database) couples storage to one consuming context and fails when the data is emitted to a different context.

**Citation:** `OWASP-ASVS V1.1.1` (canonical form decoding once) + `OWASP-ASVS V1.1.2` (encoding as a final step before the consuming interpreter).

**Plain-language impact:** Without canonical-form discipline, the same string flows through the system in three different encoded states. The validation regex sees one form; the database sees another; the rendering layer sees a third. An attacker chooses an encoding that the validator decodes harmlessly and the consumer interprets dangerously — the validator says "no `<script>` here" because it's looking at `%3Cscript%3E`. Without encode-at-boundary discipline, pre-encoded data sometimes round-trips through a system that re-encodes, producing `&amp;amp;` artifacts visible in the UI — the cosmetic bug is the visible tip of the architectural error.

**Extended discussion:** The two failure modes pull in opposite directions. *Pre-encoding* couples storage to a consuming context (HTML-escaped text in the DB renders fine on the web but corrupts in JSON APIs, CSV exports, or email). *Multi-stage decoding* lets attackers choose an encoded form that the validator misses but the consumer interprets (canonical XSS evasion). The fix is the same: decode to canonical once at the boundary on input; store and process canonical; encode at the consuming boundary on output. The two rules pair: `security-input-validation` Rule 5.4 *rejects* malformed input at the input boundary; this rule's discipline ensures canonical-form data is *encoded* on the way out.

**Related anti-patterns:** AP-1 through AP-10 in `anti-patterns.md` all depend on this rule's discipline.

## Rule 5.2: SQL — Parameterized Queries Always; ORM Parameterization Verified

**Statement:** Database queries use the driver's parameter binding mechanism — `?` placeholders in JDBC and Python DB-API, `$1` / `$2` in Node `pg`, `:name` in named-binding drivers, ORM-native binding (`Model.where(name: name)` in Rails, `User.objects.filter(name=name)` in Django, `db.query.users.findFirst({ where: { name } })` in Drizzle / Prisma). String concatenation, f-strings, `.format()`, and template literals into queries are forbidden — for SELECT, INSERT, UPDATE, DELETE, DDL, and stored-procedure invocations. ORM raw-query escape hatches (`Sequelize.query()`, `SQLAlchemy.text()`, `Knex.raw()`, Django `.raw()`, ActiveRecord `find_by_sql`) require the same parameter binding — passing user input into the raw-query string bypasses the ORM's parameterization. NoSQL injection (MongoDB query operator injection via untrusted `$where`/`$regex`), GraphQL injection (untrusted-built queries), Cypher injection, HQL injection, and DSL injection in any query language are the same class of risk and the same discipline.

**Citation:** `OWASP-ASVS V1.2.4` (parameterized queries / ORMs / entity frameworks protect against database injection) + `OWASP-CHEAT-SQLI` Defense Option 1 (Prepared Statements with Parameterized Queries — the cheat sheet's highest-priority defense) + `CWE-89` (SQL Injection).

**Plain-language impact:** SQL injection remains in the OWASP Top 10 across every iteration because it's a category of risk, not a single bug — every query is an opportunity to reintroduce it. The pattern that creates it is uniform: data and SQL syntax flow through the same channel (the query string) and the database can't tell them apart. Parameterization gives them separate channels; the database receives the query template with placeholders, then receives the parameter values as separate inputs that are *guaranteed* not to be interpreted as SQL. The fix scales to any query language with a similar primitive (NoSQL operators, GraphQL variables, Cypher parameters). The absence — a single concat-style query in a codebase otherwise disciplined — is enough to open the entire database.

**Extended discussion:** The SQL Cheat Sheet ranks defenses explicitly: Option 1 (parameterized queries) is the primary; Option 2 (stored procedures, when implemented safely) is equivalent; Option 3 (allow-list input validation) is a fallback for cases where binding can't be used (DDL identifiers, column names); Option 4 (escaping) is "STRONGLY DISCOURAGED." TGF inverts the framing: Option 1 is the universal default; the others appear only with explicit rationale documented in `WAIVER-LOG.md`. ORM safety is an empirical property, not an axiom — verify by reading the driver layer or query log, not by trusting the ORM marketing. ORM raw-query escape hatches exist for legitimate reasons (complex queries the ORM can't express) and require the same parameter binding the ORM applies to its native queries.

**Related anti-patterns:** AP-1 (SQL string concat / f-string / template literal); AP-2 (ORM raw-query escape hatch with interpolated input).

## Rule 5.3: HTML — Context-Aware Auto-Escaping; Resist Unsafe Sinks

**Statement:** HTML output uses the framework's context-aware auto-escape: React JSX text content, Angular interpolation (`{{ }}`), Vue mustache, Svelte text bindings, Jinja2 with `autoescape=True`, Django templates (autoescape default-on), Mustache `{{}}`-strict (not `{{{}}}`-unescaped). The five HTML contexts each require different encoding: (1) HTML element body — HTML entity encode (`< > & " '`); (2) HTML attribute — encode quotes and watch unquoted attributes; (3) JavaScript inside `<script>` — Unicode-escape or strict JSON serialization, not HTML entity encoding; (4) CSS inside `<style>` — CSS hex escape; (5) URL inside `href` / `src` — URL-component encoding plus safe-protocol allow-list (Rule 5.4). Unsafe sinks (`dangerouslySetInnerHTML` in React, `v-html` in Vue, `unsafeHTML` in Lit, Polymer `htmlLiteral`, Angular `bypassSecurityTrustHtml` / `bypassSecurityTrustScript` / `bypassSecurityTrustResourceUrl`, browser `innerHTML =` / `outerHTML =`, `document.write()`) require sanitization with a vetted library (DOMPurify on the client; `bleach` in Python; `sanitize-html` in Node; OWASP Java HTML Sanitizer) — not raw user data.

**Citation:** `OWASP-ASVS V1.2.1` (HTML / HTML attribute / HTML comment / CSS / HTTP header context encoding) + `OWASP-ASVS V1.2.3` (JavaScript content including JSON encoding) + `OWASP-ASVS V1.3.1` (WYSIWYG HTML input sanitization with well-known library) + `OWASP-CHEAT-XSS` §Output Encoding (lists five contexts: HTML, HTML Attribute, JavaScript, CSS, URL) + `OWASP-CHEAT-XSS` §HTML Sanitization (DOMPurify reference) + `OWASP-CHEAT-XSS` §Framework Security (React `dangerouslySetInnerHTML`, Angular bypass functions, Lit `unsafeHTML`, Polymer `htmlLiteral` enumerated as bypass surface) + `CWE-79` (Cross-Site Scripting).

**Plain-language impact:** XSS remains a top-five risk because HTML mixes content and code via syntactic markers (`<`, `>`, `&`, quotes). Auto-escape encodes those markers so user-supplied content cannot become syntax. The framework's auto-escape is comprehensive when used — and trivially bypassed when the developer reaches for `dangerouslySetInnerHTML` because they want to render formatted content. Sanitization libraries (DOMPurify, Bleach) exist for that case: they parse the HTML, walk the tree, and remove anything not in an allow-list of safe tags and attributes. The trap is conflating sanitization with auto-escape — they're complementary, not interchangeable. Auto-escape encodes; sanitization removes. Both have a place; mixing them or skipping the sanitization step on bypass APIs reopens the injection class.

**Extended discussion:** *The five HTML contexts.* Manual `str.replace('<', '&lt;').replace('>', '&gt;')` handles element body and fails the other four — attribute context needs quote encoding (and breaks completely for unquoted attributes); JavaScript context needs `\u00XX` escape or `JSON.stringify`; CSS context needs CSS hex escape (`\26` for `&`); URL context needs `encodeURIComponent` *plus* protocol allow-list. The frameworks handle this by tracking which context they're rendering into and choosing the correct encoding automatically — which is what makes auto-escape worth reaching for. *Unsafe sinks.* Per the XSS Cheat Sheet's §Framework Security: React `dangerouslySetInnerHTML` and Angular `bypassSecurityTrust*` are explicitly enumerated as patterns where the framework's protection is opted out of; Lit `unsafeHTML` and Polymer `htmlLiteral` similarly. The discipline is using these *only* with already-sanitized HTML (DOMPurify return value, server-rendered trusted markup) — never with raw user input. *Safe sinks for DOM manipulation.* The Cheat Sheet recommends `.textContent` (HTML contexts), `.setAttribute()` (attribute contexts), `style.property = x` (CSS), and `window.encodeURIComponent(x)` (URL) for direct DOM work that bypasses framework templating.

**Related anti-patterns:** AP-3 (`dangerouslySetInnerHTML` / `v-html` / unsafe sinks); AP-4 (manual HTML escape via `str.replace`).

## Rule 5.4: URL Construction — Encode per Component; Safe-Protocol Allow-List

**Statement:** URL components are encoded by position. Path segments are encoded via `encodeURIComponent` / `urllib.parse.quote(safe='')` / `java.net.URLEncoder.encode`; query parameters use the URL-building API (`new URL(...)` + `searchParams.set`; `URI.create(...)` + builder; Python `urllib.parse.urlencode`) rather than string concatenation; fragment components likewise. For URLs going *outbound* (HTTP redirects via the `Location` header, link targets in user-rendered HTML, fetch/curl/HTTP-client destinations, image `src` / iframe `src` / script `src` references), the protocol is validated against a safe allow-list — typically `https:` (and `http:` for some development or intra-net contexts). The dangerous protocols are explicit: `javascript:` (XSS via clickable link), `data:` (XSS via inline document), `vbscript:` (legacy IE XSS), `file:` (local-file disclosure in some contexts), and arbitrary absolute redirects to attacker-controlled domains (open-redirect → phishing, OAuth token theft, session fixation). For server-side requests (server fetches a URL the client supplied), the allow-list extends to host, port, and path to defeat SSRF (V1.3.6 overlap — see `security-attack-surface` Phase 7 for SSRF depth).

**Citation:** `OWASP-ASVS V1.2.2` (URL encoding by context, safe URL protocols only) + `OWASP-ASVS V1.3.6` (SSRF protection via allow-list of protocols, domains, paths, ports) + `OWASP-CHEAT-XSS` §Output Encoding for URL Contexts.

**Plain-language impact:** URLs are the most commonly underestimated injection surface. Developers see "it's a string, I'll concatenate" without recognizing that `javascript:alert(1)` in an `<a href>` is XSS, that `?redirect=https://evil.com` is open-redirect (and a phishing primitive), and that user-supplied URLs the server fetches can reach internal services (SSRF → cloud metadata service → cloud credentials). The fixes are uniform: encode by component (don't trust raw concatenation); validate the protocol (allow-list `https:` and reject everything else); for server-fetched URLs, additionally validate host and path.

**Extended discussion:** The protocol allow-list is the primary line of defense — refusing `javascript:` at the source eliminates XSS-via-href as an attack class entirely. The path-segment encoding handles spaces, special characters, and Unicode without creating malformed URLs. The query-parameter API handles `=` and `&` correctly without the developer needing to remember the escape rules. The fragment-component handling is similar. The browser will gladly follow a malformed URL to *somewhere* — the encoding discipline is what ensures *somewhere* is what was intended. For OAuth and SSO flows specifically, the redirect-URL allow-list is critical: the OAuth callback URL must match an allow-list to prevent token theft via attacker-controlled redirect.

**Related anti-patterns:** AP-5 (URL via concat; no safe-protocol allow-list).

## Rule 5.5: OS Process — Argument Arrays via execFile-Style APIs; No Shell-String Interpolation

**Statement:** Process spawning uses the structured-argument form, in which command and arguments are passed as separate list elements directly to the OS without involving a shell. Per language: **Node** — `child_process.execFile(cmd, [arg1, arg2])` or `child_process.spawn(cmd, [args])` without the `shell: true` option; never `child_process.exec(cmdString)` for any caller with untrusted-data influence. **Python** — `subprocess.run([cmd, arg1, arg2])` without `shell=True`; never `subprocess.run(cmdString, shell=True)` with untrusted data. **Java** — `new ProcessBuilder(cmd, arg1, arg2).start()` or `Runtime.exec(String[])`; never `Runtime.exec(String)` (single-string form invokes the shell on some platforms). **Go** — `exec.Command(cmd, args...)`; never `exec.Command("bash", "-c", cmdString)` with interpolation. **.NET** — `Process.Start` with `ProcessStartInfo { FileName, Arguments }` constructed via argument-list helpers; on .NET 6+ prefer `ArgumentList` to `Arguments` to avoid string-quoting pitfalls. **PHP** — prefer `proc_open` with argument array (PHP 7.4+) or `escapeshellarg` on each value before `escapeshellcmd`; never raw `shell_exec($cmdString)` or `system($cmdString)` with user input. Shell-string interpolation in any form (`exec(cmd + arg)`, `shell=True`, `bash -c "cmd $arg"`, `cmd /c "$arg"`) is forbidden for callers with untrusted-data influence — the shell is a re-interpreter and re-tokenizer that the attacker controls.

**Citation:** `OWASP-ASVS V1.2.5` (OS command injection protection via parameterized OS queries or contextual command-line output encoding) + `OWASP-CHEAT-OSI` Defense Option 1 (Avoid calling OS commands directly — highest priority) + Defense Option 3 (Parameterization in conjunction with Input Validation) + `CWE-78` (OS Command Injection).

**Plain-language impact:** OS command injection is one of the highest-impact injection classes — code execution on the host, often as the application user (which is often more privileged than expected on small projects). The pattern that creates it is uniform: a shell string is built by concatenating a command with user-controlled values, and the shell re-tokenizes the string before execution. Argument arrays bypass the shell entirely: the OS receives `execve(cmd, ["cmd", "arg1", "arg2"])` and arguments are passed as discrete parameters. The fix doesn't depend on guessing every shell metacharacter; it removes the shell from the picture. The Cheat Sheet's Defense Option 1 ("avoid calling OS commands directly") is the strongest possible discipline — when the operation can be done via a library (file operations, network operations, archive operations), the library should be used in preference to spawning a process at all.

**Extended discussion:** *When a shell is genuinely needed.* Some legitimate use cases require shell features (pipes, redirections, glob expansion). For these, either: (a) implement the equivalent without the shell (e.g., Python file iteration instead of `ls | grep`); or (b) parameterize what the shell would otherwise interpolate (e.g., pass file paths via stdin, environment variables, or temp files rather than command-line arguments). *Per-OS escape functions exist as fallback.* PHP `escapeshellarg`, Ruby `Shellwords.escape`, the Python deprecated `pipes.quote` — these are Cheat Sheet Defense Option 2, recommended only when avoiding the shell is impossible and the language doesn't offer argument-array APIs. They are correct in narrow conditions and brittle in general; the argument-array form is the universal answer.

**Related anti-patterns:** AP-6 (shell-string spawn — `exec`, `shell=True`, `bash -c`).

## Rule 5.6: Directory Services — RFC-Compliant LDAP Escaping or Parameterized Libraries

**Statement:** LDAP search filters escape per RFC 4515 §3 (LDAP String Representation of Search Filters) — the characters `*`, `(`, `)`, `\`, and `NUL` are escaped as `\2A`, `\28`, `\29`, `\5C`, `\00` respectively when they appear in attribute-value data. Distinguished Names escape per RFC 4514 §2.4 (LDAP String Representation of Distinguished Names) — `\`, `#`, `+`, `<`, `>`, `,`, `;`, `"`, `=`, and leading/trailing spaces are escaped with a leading backslash. Prefer parameterized LDAP libraries that handle this automatically: OWASP ESAPI Java Encoder (`encoder.encodeForLDAP(input)`, `encoder.encodeForDN(input)`); .NET `AntiXssEncoder.LdapFilterEncode(input)`, `AntiXssEncoder.LdapDistinguishedNameEncode(input)`; "LINQ to LDAP" with placeholder syntax; Python `ldap3` library's `escape_filter_chars()` and `escape_rdn()`. String concatenation into a filter or DN — `(&(uid=" + username + ")(objectClass=person))` — is forbidden for callers with untrusted-data influence.

**Citation:** `OWASP-ASVS V1.2.6` (LDAP injection protection or specific security controls implemented) + `OWASP-CHEAT-LDAP` §Primary Defenses (escape filter/DN per RFC standards; use frameworks that automatically protect) + `RFC-4515` §3 (search filter character escaping) + `RFC-4514` §2.4 (DN character escaping) + `CWE-90` (LDAP Injection).

**Plain-language impact:** LDAP injection is the directory-services equivalent of SQL injection. A filter like `(&(uid=USER)(objectClass=person))` becomes `(&(uid=*)(uid=*)(objectClass=person))` when the username is `*)(uid=*` — the filter now matches every user, and an authentication check using that filter authenticates anyone. Filter injection in LDAP is *less* common in code review than SQL injection (LDAP is less common as a backend) but *more* impactful when it occurs — the directory often controls authentication and group membership, so a single LDAP injection can compromise the access-control mesh of the entire application. The fix mirrors SQL: escape per the RFC standard, or use a library that parameterizes; never concatenate into the filter or DN.

**Extended discussion:** *Filter context (RFC 4515) vs DN context (RFC 4514) — different escape sets.* The two characters classes are not interchangeable; using the wrong escape leaves the wrong characters unescaped. ESAPI distinguishes them explicitly (`encodeForLDAP` vs `encodeForDN`); .NET likewise (`LdapFilterEncode` vs `LdapDistinguishedNameEncode`). *Active Directory specifics.* AD layers additional rules on top of RFC 4514 for some attribute types; the .NET encoder is RFC 2253-compliant (the predecessor RFC) which AD honors. *Cross-reference forward to authentication.* If LDAP is the authentication backend, `security-iam-authentication` (Phase 6) carries the credential-verification discipline; this rule covers only the encoding side.

**Related anti-patterns:** AP-7 (LDAP filter built via string concatenation).

## Rule 5.7: Long-Tail Injection Contexts — XML, XPath, CSV, Templates, Logs

**Statement:** Every parsed or interpreted output context is an injection class with its own encoding discipline. **XML serialization and parsing:** XML parsers disable external-entity resolution and DTD loading by default — Python `xml.etree.ElementTree.XMLParser(resolve_entities=False)` (or use `defusedxml` library); Python lxml `etree.XMLParser(resolve_entities=False, no_network=True)`; Java `SAXParser` / `DocumentBuilder` with `setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` and `setFeature("http://xml.org/sax/features/external-general-entities", false)` and `setFeature("http://xml.org/sax/features/external-parameter-entities", false)`; Node `libxmljs` or `fast-xml-parser` with explicit no-entity options. **XPath queries:** parameterized via variable-binding APIs (Java `XPathExpression.setVariable`, Python `lxml.etree.XPath` with `variables=` parameter, .NET `XPathExpression` with `XmlNamespaceManager`); never built via string concatenation. **CSV / spreadsheet exports:** field values whose first character is `=`, `+`, `-`, `@`, `\t` (tab), or `\0` (null) are escaped with a leading single quote (`'`) per RFC 4180 §2.6 / §2.7 conventions; alternatively, the field is prefixed with a non-formula character to defeat formula injection (CSV → Excel / Google Sheets / LibreOffice). **Server-side templates:** template strings are not built from untrusted input — server-side template injection (SSTI) is the result of `render_template_string(user_input)` patterns; user-controllable data is passed *to* templates as parameters, not used to *construct* templates. **Log lines:** user-controlled values reaching log emission are encoded for the logger's format — CR/LF and control characters removed or hex-escaped (`\r\n` → `\\r\\n` literal) to defeat log injection / forging; structured logging (`logger.info(event="login", user=user_id)`) is the canonical pattern because the structured-field API handles encoding. Cross-references: deeper deserialization safety in `security-input-validation` Rule 5.4 (rejection at input); deeper logging discipline (sensitive-data scrubbing, retention) in `security-logging` Phase 6.

**Citation:** `OWASP-ASVS V1.5.1` (XML parser restrictive configuration to prevent XXE) + `OWASP-ASVS V1.2.7` (XPath injection protection via query parameterization or precompiled queries) + `OWASP-ASVS V1.2.10` (CSV / spreadsheet formula injection — Level 3) + `OWASP-ASVS V1.3.7` (template injection — templates not built from untrusted input) + `RFC-4180` §2.6 and §2.7 (CSV field escaping) + `CWE-611` (XXE — Improper Restriction of XML External Entity), `CWE-643` (XPath Injection), `CWE-117` (Improper Output Neutralization for Logs), `CWE-1336` (Improper Neutralization of Special Elements Used in a Template Engine).

**Plain-language impact:** The long-tail contexts each look obscure individually and add up to a large fraction of injection vulnerabilities in practice. XXE in default-configured XML parsers reads arbitrary files from the server (`/etc/passwd`, AWS metadata service tokens); XPath injection in LDAP-replacement directories or XML databases breaks authentication just like SQL injection in relational databases; CSV formula injection turns "user fills in their bio" into "spreadsheet runs an `=cmd|/c calc` formula when an admin opens the export" (real CVE class); SSTI lets an attacker execute Python or Ruby on the server when templates are built from untrusted input; log injection forges entries to confuse incident response. The unifying discipline is the same: identify the consuming interpreter, apply its encoding standard, do not concatenate.

**Extended discussion:** *XXE specifically.* The default behavior of Java's `DocumentBuilderFactory`, Python's `xml.etree`, and Node's `libxmljs` historically allowed external entity resolution — fetching DTDs and entity values from URLs. The fix is parser configuration; the use of `defusedxml` (Python) or `OWASP Java XML Security` libraries (Java) is the easier path than per-parser hardening. *XPath specifically.* Modern XML processing is rarer than SQL but identical in pattern — string-built XPath queries with user input are injectable; variable-binding APIs solve it. *CSV formula injection.* Discovered widely after 2014; the leading-character escape (single quote prefix) is the RFC-4180-conformant pattern. Many CSV-writing libraries (Python's csv module, Node's csv-stringify) do not escape formula characters by default — the developer must apply the escape per field or use a library that handles it. *Log injection.* The discipline is part of the broader logging hygiene that `security-logging` covers; encoding is the narrow CWE-117 concern this rule addresses.

**Related anti-patterns:** AP-8 (XML parser with XXE enabled by default); AP-9 (CSV formula injection on export); AP-10 (log injection via unencoded CR/LF in user-controlled log content). Template injection is forward-referenced to `security-input-validation` Rule 5.4 (reject untrusted-built templates at input).
