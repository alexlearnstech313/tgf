# SECURITY-CRYPTOGRAPHY — Rules

Seven rules extending SECURITY-CORE Rule 5.3 (*Use Established Cryptography; Never Roll Your Own*) and Rule 5.5 (*TLS Verification Always Enabled, Strong Defaults*) with operational depth. SECURITY-CORE remains canonical for the universal principles; the rules below specify *which* algorithms, parameters, and lifecycles.

Per Phase 6 Checkpoint 1 Decision A: chapter-level citations live in `SKILL.md §2 Authoritative Sources`; sub-rule citations (V11.x.y, V12.x.y) appear here.

Per Phase 6 Checkpoint 1 Decision B: hard-refusal patterns covered by SECURITY-CORE APs (AP-2 custom crypto, AP-3 disabled TLS, AP-4 broken algorithms) are referenced rather than restated.

---

## Rule 5.1: Approved Algorithms by Purpose — AES-GCM, Argon2id, Ed25519, SHA-256/SHA-3

**Statement:** Cryptographic operations use approved algorithms chosen by purpose. **Symmetric authenticated encryption:** AES-GCM (preferred), AES-CCM, or ChaCha20-Poly1305. **Password hashing / key derivation from passwords:** Argon2id (OWASP-preferred), scrypt, or bcrypt — never general hash functions. **Digital signatures:** Ed25519 (preferred), RSA-PSS, or ECDSA on NIST P-256 / P-384. **General-purpose hashing (HMAC, digital signature digest, file integrity, content-addressing):** SHA-256, SHA-384, SHA-512, or SHA-3 family. **Key agreement / key exchange:** ECDH on Curve25519 (X25519) or NIST P-256. **Key derivation from another key:** HKDF (RFC 5869). **Key wrapping:** AES-KW or AES-GCM. The forbidden algorithms (per OWASP ASVS V11.3.1, V11.4.1, and SECURITY-CORE Rule 5.3) for security purposes: MD5, SHA-1, DES, 3DES, RC4, ECB mode for confidentiality, PKCS#1 v1.5 padding for RSA.

**Citation:** `OWASP-ASVS V11.2.1` (industry-validated cryptographic implementations) + `V11.3.1` (prohibit insecure block modes ECB and weak padding PKCS#1 v1.5) + `V11.3.2` (approved ciphers and modes like AES-GCM) + `V11.4.1` (approved hash functions; prohibit MD5) + `V11.6.1` (approved algorithms for key generation, seeding, digital signatures); extends `SECURITY-CORE Rule 5.3` (use established cryptography; never roll your own); `CWE-327` (Use of Broken or Risky Cryptographic Algorithm).

**Plain-language impact:** The wrong algorithm for the purpose is one of the most common cryptographic failures — SHA-256 for passwords (fast → GPU cracking trivial), RSA-1024 still in production (broken at academic-budget scale), DES surviving in legacy code (broken in 1998), ECB mode encrypting structured data (patterns visible — the famous "ECB penguin"). The fix is choosing from the approved list at design time and verifying choice persists through implementation. The OWASP Top 10:2025 elevation of A04 (Cryptographic Failures) from "Sensitive Data Exposure" reflects the recognition that the underlying failure is algorithmic, not just exposure.

**Extended discussion:** *Algorithm vs library.* "AES-GCM" is the algorithm; the library is what provides the secure implementation. Use the library's high-level API (`crypto.subtle.encrypt` in Web Crypto, `cryptography.fernet` for high-level Python with AES-CBC+HMAC, `crypto/cipher` in Go with proper AEAD construction). Avoid low-level APIs that let you assemble the primitive yourself — that's the boundary where errors creep in. *Per-purpose selection.* The OWASP Cryptographic Storage Cheat Sheet recommends AES-GCM (or CCM) "as a first preference" for authenticated symmetric encryption. The Password Storage Cheat Sheet recommends Argon2id as primary; bcrypt acceptable when Argon2id isn't available. For signatures, Ed25519 is the modern default; ECDSA on P-256 is the FIPS-compliant alternative. *Hash function notes.* SHA-256 is the default general-purpose hash. SHA-3 (Keccak) is the alternative for parties wanting algorithm diversity. Both have 128-bit collision resistance at 256-bit output (per V11.4.3). MD5 and SHA-1 are catastrophically broken for security purposes — collision attacks practical at low cost — but acceptable for non-security uses (e.g., file deduplication where collision resistance doesn't matter).

**Related anti-patterns:** AP-1 (AES-ECB mode for confidentiality); AP-4 (password hashed with general hash — extends SECURITY-CORE AP-4); AP-6 (PKCS#1 v1.5 padding for RSA encryption). Hard-refusal: custom crypto = SECURITY-CORE AP-2; MD5/SHA-1 = SECURITY-CORE AP-4.

## Rule 5.2: 128-bit Minimum Security Strength; Cryptographic Agility for Migration

**Statement:** Every cryptographic primitive provides at least **128 bits of security strength** against the relevant attack model. Equivalent strength translates per primitive family: AES-128 (symmetric, 128-bit); RSA-3072 / ECC P-256 / DSA-3072 (asymmetric, 128-bit equivalent); SHA-256 (256-bit output, 128-bit collision resistance per V11.4.3). Stronger primitives are acceptable for new code (AES-256, RSA-4096, P-384, SHA-384) but the floor is 128. Applications are designed with **cryptographic agility** (per V11.2.2) — algorithm choice, key length, mode, and cipher parameters are configurable; swapping primitives requires configuration change, not code rewrite. **Post-quantum migration plans** are documented for long-lived secrets (per V11.1.4) — data encrypted today that needs to remain confidential beyond ~2030–2035 is a candidate for post-quantum-safe encryption (CRYSTALS-Kyber, etc.) or hybrid schemes.

**Citation:** `OWASP-ASVS V11.2.2` (crypto agility for reconfiguration), `V11.2.3` (minimum 128 bits of security), `V11.1.4` (inventory + migration plans to post-quantum cryptography); `CWE-326` (Inadequate Encryption Strength).

**Plain-language impact:** Insufficient strength is the failure mode that becomes visible only at attacker-budget scale. RSA-1024 was the standard in the early 2000s and is now factorable at academic-research budget; 80-bit symmetric keys (DES-relative) likewise. Today's "good enough" becomes tomorrow's "trivially broken" — the discipline of 128-bit minimum is forward-looking. The cost is modest (AES-128 vs DES; SHA-256 vs SHA-1; RSA-3072 vs RSA-1024 — small performance differences); the benefit is decades of safety margin.

**Extended discussion:** *NIST SP 800-175B Rev 1.* The federal-government guideline for cryptographic mechanisms; cross-references SP 800-57 for key management. Both are authoritative for the 128-bit floor and the per-algorithm equivalency tables. *Post-quantum cryptography (PQC).* NIST has selected initial PQC standards (Kyber for key encapsulation, Dilithium for signatures, SPHINCS+ as a stateless hash-based alternative) as of 2024. For data with a long confidentiality window, the consideration is "store-now-decrypt-later" — an attacker recording encrypted traffic today and decrypting once quantum hardware is practical. Hybrid schemes (classic + PQC in parallel) are the conservative path. *Agility implementation.* In code, agility looks like: the encryption function takes algorithm parameters from configuration, the configuration declares the current default, migration involves changing config + re-encrypting where needed; in storage, multi-version records (`v: 2, algo: aes-256-gcm`) let new records use new defaults while old records remain readable.

**Related anti-patterns:** No direct AP — this rule is preventive against future-strength failures. Hardcoded weak parameters surface in AP-5 (insufficient KDF parameters); legacy algorithms surface in AP-6 (PKCS#1 v1.5).

## Rule 5.3: Authenticated Encryption Only; IV/Nonce Uniqueness Mandatory

**Statement:** Symmetric encryption uses **authenticated encryption modes** (AEAD): AES-GCM, AES-CCM, ChaCha20-Poly1305. The authentication tag is verified before the decrypted plaintext is used; tag-verification failure means the ciphertext is rejected (not "almost decrypt and fall back"). When AEAD is not available (legacy interop), encrypt-then-MAC is the only acceptable construction: AES-CBC for confidentiality, HMAC-SHA-256 over the ciphertext-and-IV for authentication, verified before decryption (per V11.3.5 encrypt-then-MAC mode). **IVs and nonces are unique per (key, message) pair** (per V11.3.4). For AES-GCM specifically, **IV reuse under the same key is catastrophic** — a single repeated IV under the same key reveals the GHASH authentication key, allowing the attacker to forge arbitrary authenticated messages under that key. The discipline is **random IVs from CSPRNG** (12 bytes for AES-GCM, providing collision resistance up to ~2^32 messages per key) or **strictly monotonic counters that never restart** (carefully managed for distributed systems). Salts likewise — unique per password/use, generated from CSPRNG, stored alongside the hash.

**Citation:** `OWASP-ASVS V11.3.2` (only approved ciphers and modes — AES-GCM example), `V11.3.3` (protect encrypted data against unauthorized modification — AEAD or encryption+MAC), `V11.3.4` (nonces/IVs/single-use numbers not reused across encryption key/data pairs), `V11.3.5` (encryption + MAC operate in encrypt-then-MAC mode); `CWE-323` (Reusing a Nonce, Key Pair in Encryption).

**Plain-language impact:** Unauthenticated encryption is malleable — the attacker can modify the ciphertext and the recipient won't notice. Padding-oracle attacks (Bleichenbacher 1998; POODLE 2014; lucky-13 against TLS-CBC) all exploit this. AEAD addresses both confidentiality and integrity in one primitive. IV/nonce reuse is the second catastrophic failure: with AES-GCM under the same key, two messages with the same IV let an attacker XOR the ciphertexts to recover plaintext XOR, and (worse) recover the GHASH authentication key for forgery. Salt reuse for password hashing eliminates the per-user-cost amplification — one rainbow table works across all users with the same salt.

**Extended discussion:** *Why AES-GCM specifically.* GCM (Galois/Counter Mode) is hardware-accelerated on modern CPUs (AES-NI + CLMUL); it's an IETF standard for TLS 1.3, IPsec, SSH. *Nonce sizing.* For AES-GCM, the standard 12-byte (96-bit) IV is the right choice — gives 2^32 messages per key before collision risk becomes noticeable, and avoids the GCM nonce-extension code path. *Counter vs random IVs.* Counter-based IVs are safe in principle but operationally fragile in distributed systems (multiple writers, state recovery after crash). Random IVs from CSPRNG are simpler and safer at acceptable performance cost. *Encrypt-then-MAC vs encrypt-and-MAC vs MAC-then-encrypt.* The order matters: encrypt-then-MAC computes the MAC over the ciphertext (resists chosen-ciphertext attacks); the other orderings have known weaknesses against various attacker models. V11.3.5 mandates encrypt-then-MAC specifically.

**Related anti-patterns:** AP-1 (AES-ECB mode — unauthenticated *and* non-randomized); AP-2 (IV/nonce reuse with AES-GCM — the catastrophic case).

## Rule 5.4: CSPRNG for All Security-Relevant Random Values

**Statement:** All random values used for security purposes — authentication tokens, session IDs, nonces, IVs, salts, password-reset tokens, OAuth state, JWT IDs (`jti`), CSRF tokens, key material generated by the application, and any value where unpredictability matters for security — come from the language's **cryptographically secure pseudorandom number generator (CSPRNG)**. Per language: Node `crypto.randomBytes(n)` or `crypto.randomUUID()` (Node 14.17+); Python `secrets.token_bytes(n)` / `secrets.token_urlsafe(n)` / `secrets.token_hex(n)`; Java `java.security.SecureRandom`; Go `crypto/rand.Reader`; .NET `System.Security.Cryptography.RandomNumberGenerator`; Ruby `SecureRandom.bytes(n)` / `SecureRandom.urlsafe_base64(n)`; Rust `rand::rngs::OsRng` (or `getrandom` crate). **Forbidden for security purposes:** `Math.random()` (JavaScript), `random.random()` / `random.randint()` (Python `random` module), `rand()` (C / C++ stdlib), `java.util.Random` (Java non-secure PRNG), `math/rand.Intn()` (Go non-secure PRNG), `Random.new` (Ruby non-secure), `rand::thread_rng()` (Rust — fine for non-security; CSPRNG status varies). Minimum **128 bits of entropy** per generated value (per V11.5.1); UUIDs (which are 128-bit but include version/timestamp bits) do not satisfy this requirement on their own.

**Citation:** `OWASP-ASVS V11.5.1` (CSPRNG with minimum 128 bits of entropy; UUIDs do not satisfy this requirement); `OWASP-CHEAT-CS` (language-specific CSPRNG examples — SecureRandom, secrets, crypto.randomBytes); `CWE-330` (Use of Insufficiently Random Values).

**Plain-language impact:** Non-cryptographic PRNGs are designed for speed and statistical-distribution quality, not for unpredictability. `Math.random()` uses an algorithm (typically xorshift128+ in V8) where after observing 5–10 outputs, the entire future sequence can be reconstructed. A session-ID generator that uses `Math.random()` lets an attacker who guesses one session ID (or observes one) predict all other session IDs being generated in that runtime. Token generators similarly. The fix is one-line: swap `Math.random()` for `crypto.randomBytes()`. The miss happens because both function names contain "random" and AI training data has both patterns intermixed.

**Extended discussion:** *Why UUIDs alone don't satisfy 128-bit entropy.* UUID v4 has 122 bits of randomness (6 bits fixed for version/variant). 122 bits is *almost* 128 and considered safe in practice for most uses — but ASVS V11.5.1 calls out UUIDs specifically because UUIDs sometimes use predictable timestamp / MAC-address fields (v1, v3, v5). For unambiguous compliance, use `crypto.randomBytes(16)` or equivalent. *UUID v7.* Time-ordered UUID format introduced 2024; includes timestamp + 62 bits randomness. Useful for database-key ordering; not a substitute for token entropy. *Constant-time considerations.* CSPRNG output should be compared in constant time when used as a security check (e.g., comparing a presented token to the stored token); see Rule 5.7 cross-reference for `crypto.timingSafeEqual`. *State of CSPRNG.* CSPRNGs draw from OS entropy pools (`/dev/urandom` on Unix; `BCryptGenRandom` on Windows). On constrained environments (containers without `/dev/urandom`, early boot), entropy can be limited — modern stacks handle this transparently, but legacy environments need verification.

**Related anti-patterns:** AP-3 (non-CSPRNG `Math.random` / `rand` / `Random` for security values).

## Rule 5.5: Password Hashing Uses Memory-Hard KDFs with Tuned Parameters

**Statement:** Passwords are hashed with a **memory-hard key derivation function (KDF)**: **Argon2id (OWASP-preferred)**, scrypt, or bcrypt. Never with general-purpose hash functions (SHA-256, SHA-512, SHA-3) — even with salt — because general hashes are fast (GPU-cracking computes billions per second). Memory-hard KDFs use both CPU time and memory per attempt, defeating GPU/ASIC acceleration. **Current parameter guidance (OWASP Password Storage Cheat Sheet, verified 2026-05-22):** Argon2id ≥ 19 MiB memory, 2 iterations, 1 parallelism (minimum; alternative sets at higher memory / fewer iterations all equivalent — 47 MiB / t=1, 12 MiB / t=3, 9 MiB / t=4, 7 MiB / t=5); bcrypt cost ≥ 10 (work factor "as large as verification server performance will allow"); scrypt N ≥ 2^17 (128 MiB), r=8, p=1 (primary; alternative sets at smaller N + higher p); PBKDF2-HMAC-SHA-256 ≥ 600,000 iterations (acceptable for FIPS contexts; PBKDF2-HMAC-SHA-512 ≥ 220,000 alternative). **Salt:** unique per password, generated via CSPRNG, ≥ 16 bytes, stored alongside the hash (modern KDF libraries handle salt automatically). **Pepper:** an application-wide secret stored separately from the database (in secrets vault or HSM) combined with the password before hashing — defense-in-depth against database-only compromise; not a substitute for KDF cost.

**Citation:** `OWASP-ASVS V11.4.2` (computationally intensive key derivation functions with balanced parameters), `V11.4.4` (approved KDFs with key stretching parameters when deriving secret keys from passwords); `OWASP-CHEAT-PS` (Password Storage Cheat Sheet — Argon2id recommendation + current parameter table); `CWE-916` (Use of Password Hash With Insufficient Computational Effort).

**Plain-language impact:** Database breaches happen. When they happen, the value of the password column depends entirely on how the passwords were hashed. SHA-256(password+salt) at modern GPU rates: ~10 billion guesses/second on a single high-end GPU; ~500 billion on a small farm. A typical user password (top 1M wordlist with simple mutations) cracks in seconds. Argon2id at recommended parameters: ~10–100 guesses/second per GPU thread, hundreds-of-millions of times slower. The breach doesn't become "everyone's passwords are exposed in plaintext"; it becomes "weak passwords are guessable within months, strong passwords stay safe for years." The cost difference per legitimate login is microseconds-vs-milliseconds — acceptable for the threat-multiplier benefit.

**Extended discussion:** *Why memory-hard.* GPU and ASIC acceleration is the threat — both can compute parallel hashes orders of magnitude faster than CPUs. Memory-hard functions require state proportional to the parameter; GPUs have less memory per core than CPUs, so the per-attempt advantage shrinks dramatically. Argon2id won the Password Hashing Competition (2015) on this basis. *Parameter tuning.* The OWASP Cheat Sheet's parameters are minimums; tune higher for production (target ~100ms per legitimate verification on the slowest acceptable hardware). *Migrating from weaker hashes.* Production systems with legacy SHA-256-hashed passwords cannot mass-rehash without the plaintext. Migration pattern: on next user login, verify against the legacy hash; if it matches, immediately re-hash with Argon2id and update the stored value. Within a few months of regular usage, most accounts have migrated; long-dormant accounts stay on the legacy hash until they next log in. *Pepper considerations.* Pepper is stored in application config (HSM, secret manager) and not in the database; an attacker with database-only access cannot compute valid hashes without also having the pepper. Pepper rotation is harder than salt rotation; treat it as a high-trust secret.

**Related anti-patterns:** AP-4 (password hashed with general hash — no key stretching); AP-5 (PBKDF2 / bcrypt / scrypt with insufficient parameters).

## Rule 5.6: Key Lifecycle — Generation, Separation, Rotation, Destruction

**Statement:** Cryptographic keys have **lifecycles** managed in alignment with NIST SP 800-57 Part 1 Rev 5. **Generation:** symmetric keys via CSPRNG (`crypto.randomBytes(32)` for AES-256); asymmetric keys via library-native key-generation functions (`crypto.generateKeyPair` in Node, `cryptography.hazmat.primitives.asymmetric` in Python). **Separation by purpose:** a key used for encryption is *not* the same key used for HMAC; a signing key is *not* the same key used for encryption; key-encrypting keys (KEK) are separate from data-encrypting keys (DEK). The **KEK/DEK pattern** is the canonical structure for data-at-rest: each data item has its own DEK; DEKs are encrypted by the KEK; KEK rotation re-encrypts (small) DEKs, not (large) data. **Rotation:** scheduled per NIST SP 800-57 §5.3 cryptoperiods — symmetric encryption keys typically 1–2 years; signing keys per use-case (typically 1–3 years for code-signing, shorter for token-signing); immediate rotation on suspected compromise. **Destruction:** at end of life, keys are overwritten and the storage is destroyed unrecoverably — for KMS-managed keys, the KMS handles destruction; for application-managed keys, deliberate memory-clearing and storage-overwriting.

**Citation:** `OWASP-ASVS V11.1.1` (documented policies for key management adhering to NIST SP 800-57; prevent key oversharing), `V11.1.2` (cryptographic inventory of keys / algorithms / certificates / usage / data-protection capabilities); `NIST-SP-800-57 §5.3` (cryptoperiods), `§6` (key lifecycle); `OWASP-CHEAT-CS §Key Management` (rotation triggers — cryptoperiod, compromise, volume, algorithm break).

**Plain-language impact:** Key lifecycle management is the operational discipline that makes cryptography sustainable. Without rotation, a key compromised in year 3 exposes every message encrypted under it from years 1 onward (no forward secrecy at rest). Without separation, an attack on one purpose compromises all purposes — a key recovered via a signing oracle is *also* the encryption key. The KEK/DEK pattern makes rotation tractable at scale — you can't re-encrypt a petabyte of data, but you can re-encrypt a megabyte of DEKs. NIST SP 800-57 cryptoperiods are conservative recommendations grounded in expected attacker capability evolution over time.

**Extended discussion:** *KMS vs application-managed.* Modern applications increasingly defer key management to a cloud KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault) or HSM. The KMS handles generation, storage, rotation, destruction, and access logging — the application calls "encrypt with this key" and the cryptography happens inside the KMS boundary. Cross-reference forward to `security-secrets-management` (Phase 6 commit 5/12) for KMS integration patterns. *Key escrow.* For data the organization must retain access to after employee departure (a backup-encryption use case), a key-escrow arrangement is required — the operational key may be ephemeral, but the data-recovery key is held by trusted custodians. *Cryptoperiod by use case.* Per NIST SP 800-57 §5.3 (approximate, verify against the publication): TLS session keys — per session (seconds to hours); short-term authentication keys — months; long-term confidentiality keys — 1–5 years; signature keys for archives — much longer (up to decades for historical records). *Migration during rotation.* Rotating a key without invalidating existing tokens / sessions requires multi-key support — verify against current key AND previous key during the transition window.

**Related anti-patterns:** AP-7 (same key reused across cryptographic purposes — separation violation). Hardcoded keys: SECURITY-CORE AP-1 (hardcoded credentials).

## Rule 5.7: TLS 1.2 Minimum; 1.3 Preferred; Strong Cipher Suites; No Plaintext Fallback

**Statement:** **Inbound HTTPS servers** enforce **TLS 1.2 minimum**, prefer **TLS 1.3** (per V12.1.1). TLS 1.0, TLS 1.1, and SSLv3 are explicitly disabled (per RFC 8996 deprecation). **Cipher suites** prioritize **forward-secrecy AEAD** combinations: ECDHE-RSA with AES-GCM or ChaCha20-Poly1305; ECDHE-ECDSA with AES-GCM; TLS 1.3's modern cipher suite set (which removes most legacy options by design). **Certificate validation** is always enabled for outbound calls (extends SECURITY-CORE Rule 5.5 hard-refusal); no `verify=False` / `rejectUnauthorized: false` / `InsecureSkipVerify: true` in code that reaches production. **HSTS** (`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`) for browser-facing endpoints. **Internal service-to-service communication** uses TLS without plaintext fallback (per V12.3.1) — "internal" traffic is not exempt; the threat model in zero-trust environments treats all networks as potentially hostile. **mTLS** (client-certificate authentication) for sensitive intra-service paths (per V12.3.5). **OCSP stapling** for certificate revocation (per V12.1.4 at L3).

**Citation:** `OWASP-ASVS V12.1.1` (only current TLS versions 1.2/1.3 active, newest preferred), `V12.1.2` (recommended cipher suites; forward secrecy at L3), `V12.2.1` (TLS encrypts all HTTP traffic to external services without fallback), `V12.3.1` (encrypted protocols secure all inbound/outbound connections without fallback), `V12.3.2` (TLS clients validate received certificates before communication), `V12.3.4` (internal TLS uses trusted certificates; self-signed requires CA / pinning); `RFC-8446` (TLS 1.3); `RFC-8996` (deprecating TLS 1.0 and 1.1); extends `SECURITY-CORE Rule 5.5` (TLS verification always enabled, strong defaults).

**Plain-language impact:** TLS configuration is one of the most-checked attributes in security scans (Mozilla Observatory, SSL Labs) precisely because misconfigurations are common and consequences are direct. TLS 1.0 / 1.1 still enabled means a downgrade-attack vector (the attacker forces a renegotiation to the weakest version both sides support). Weak cipher suites (RC4, 3DES, export-grade ciphers) historically allowed cryptanalysis; modern attacks (BEAST, CRIME, BREACH, POODLE, FREAK, Logjam, lucky-13, ROBOT) are version- and cipher-suite-specific. Internal-traffic-unencrypted is the assumption that "the network is safe" — proven repeatedly false (compromised pod → all inter-pod traffic readable; cloud-provider mistake; insider threat). The discipline is uniform: TLS-protected, validated, current-protocol, AEAD-cipher-suite, no exceptions.

**Extended discussion:** *TLS 1.3 specifics.* RFC 8446 (2018) finalized TLS 1.3. Modern deployments default to 1.3 if both sides support it. 1.3 removed many problematic options (no static RSA key exchange, AEAD-only ciphers, integrated forward secrecy). *Cipher suite recommendations.* The Mozilla SSL Configuration Generator's "Modern" profile is the operational standard (TLS 1.3 + TLS 1.2 with ECDHE+AEAD only). *HSTS and HSTS Preload.* HSTS prevents protocol downgrade attacks at the browser level; preload (registering domain with `hstspreload.org`) extends the protection to the first-visit case. *Certificate pinning.* For mobile apps and sensitive APIs, certificate or public-key pinning hardens against CA-compromise attacks; comes with operational cost (key rotation requires app update). HPKP at the browser level was deprecated; mobile-app pinning persists. *Internal TLS via service mesh.* Linkerd, Istio, Cilium-mesh, and similar provide automatic mTLS for cluster traffic — preferable to per-service TLS configuration at scale. Self-signed internal certificates require explicit trust-bundle configuration on every client; the service mesh handles this automatically.

**Related anti-patterns:** AP-8 (TLS 1.0 / 1.1 still enabled); AP-9 (plaintext fallback / "internal" traffic unencrypted). Disabled TLS verification: SECURITY-CORE AP-3 (hard-refusal).
